## Findings and limits

- Baseline testing exposed harness assumptions about simulator startup: startup stale counts, old snapshots and unread diagnostic pipes. The harness now measures from observed healthy state and drains during simulator lifecycle waits. The complete baseline then passed.
- Stronger warnings exposed Linux EAGAIN/EWOULDBLOCK alias redundancy; the duplicate condition was removed. No wire behavior changed. No sanitizer/fuzzer defect was observed in the final runs.
- VM stalls can batch differing readings at the same receive timestamp and trigger the rate rule. Transport/count and silence fixtures disable that unrelated rule; deterministic C tests retain exact rate boundaries. The production receive-time plausibility policy is unchanged and this batching limitation is documented.
- A timestamped result is only accepted if its assertions and command exit status succeed; failed development runs remain in local artifacts.
- vcan exercises real Linux application behavior, not physical CAN arbitration, bitrate ceilings, electrical faults, wiring or bus-off.
- The queue is volatile: pending N readings + 256 events + at most 32 immutable in-flight records. Only pending unsubmitted records are evicted; a lost COMMIT response can leave unconfirmed rows already in SQL.
- The known stopped-database crash fixture can measure three lost readings. A restarted daemon cannot reconstruct unknown prior-run losses or emit an honest exact gap for memory that vanished. No disk spool or crash durability is claimed.
- CRC/counters do not authenticate senders. Flatness is suspicion, not proof of a failed sensor. Diagnostic regular-file I/O can still block; backpressure can drop counted output lines.
- No hardware, production scale, hard real-time, A-Link/NetBotz compatibility or Buildroot claim. The core and evidence satisfy the version 3 brief subject to the documented architectural/process refinements in DECISIONS.md.
